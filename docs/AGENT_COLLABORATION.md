# Bony 开发 Agent 协作规范

> 本规范定义编码 Agent 的分工、所有权、交接与验证。项目硬约束仍以 `docs/PROJECT_STANDARDS.md`、根 `AGENTS.md` 和 `.cursor/rules/*` 为准；Buzz 房间运行时路由另见 `docs/buzz-room-agent-orchestration-plan.md`。

## 1. 三层职责

| 层 | 位置 | 作用 | 不应承载 |
|----|------|------|----------|
| 强制规则 | `AGENTS.md`、`.cursor/rules/*` | 始终生效的语言、性能、安全、构建边界 | 长步骤教程 |
| Task Skill | `.cursor/skills/*/SKILL.md` | 按任务触发的可复用工作流 | 永久注入的项目常识 |
| 房间角色 Prompt | `scripts/buzz-room/prompts/*.md` | 运行时 specialist 的窄职责、工具与 handoff | 业务实现、重复路由引擎 |

同一事实只保留一个权威定义；其它层用链接或一句硬约束引用，不复制整段。

## 2. 任务路由

| 任务 | 主 Skill | 主责任角色 | 必要补充 |
|------|-----------|------------|----------|
| Rust 功能、修复、重构 | `rust-change-delivery` | 实现者 | Buzz 构建/启动再叠加 `buzz-room-build-gate` |
| 根因分析、故障定位 | `rust-failure-diagnosis` | 调查者 | 用户要求修复后再转实现者 |
| 延迟、吞吐、内存、I/O | `rust-performance-optimization` | 性能实现者 | 变更完成后独立评审 |
| diff / PR / 合并前评审 | `rust-change-review` | 评审者 | 默认只读，不与实现者共用结论 |
| 新增/修改 Buzz agent、用户自建 Agent | `buzz-agent-contracts` | 契约设计者 | 触及 registry/硬拦时转 Rust 实现者 |
| 上游 grok-build 同步 | `upstream-feature-sync` | 集成者 | 必须保留产品层与 Buzz 本地栈 |
| LanceDB / 向量检索 | `lancedb-best-practices` | 数据实现者 | 仍遵守 Rust 交付与性能闸门 |

命中多个 Skill 时按“诊断 → 实现/性能 → 评审 → 构建/启动验证”顺序使用，避免不同角色重复探索同一问题。

## 3. 角色契约

### 协调者

- 只在跨域或存在真实依赖时拆分任务。
- 先定义验收点、依赖图和文件/模块所有权，再派工。
- 一个文件或一个权威实现点同时只能有一个写入者。
- 共享 API、schema、`Cargo.toml`、`Cargo.lock`、规范文档由单一集成者串行修改。

### 调查者

- 默认只读，交付最小复现、根因、证据和修复面。
- 不顺手修复，不把候选假设写成确定结论。
- 找到根因后停止扩散，避免与实现者重复读全仓库。

### 实现者

- 只拥有一个有界模块或 crate 表面。
- 先复用现有实现，再写最小 Rust diff；入口薄、领域厚。
- 交付测试和用户可复现路径，不提交、不推送，除非用户明确要求。

### 评审者

- 不编辑被评审变更，避免自证式评审。
- 只报告可操作、由本次 diff 引入、能给出触发路径的问题。
- 按严重度给出文件/行、影响、证据和最小修复方向。

### 验证者 / 集成者

- 在共享契约稳定后运行 package-scoped 检查与跨 crate 验证。
- 同一根 `target/` 上只保留一个主动 Cargo 验证任务，避免锁竞争和重复编译。
- 不通过修改业务逻辑来让测试通过；失败回交给拥有该模块的实现者。

### 动态角色原则

- 上述“协调者/调查者/实现者/评审者/验证者”是职责，不是固定 Agent 名单。
- 分工优先匹配 capability、权限、健康状态和任务所有权；显示名只用于沟通。
- 内置 Agent 提供默认映射，用户自建 Agent 满足同一契约后可替换或补充，不要求修改本规范。
- 未声明 capability 的 Agent 仍可被用户显式选择，但不得被自动推断为高权限角色。
- 同一任务中仍保持一个权威写入者；Agent 数量增加不能放松文件所有权和单 `target/` 约束。

## 4. 并行与串行边界

允许并行：

- 已固定 API 后，不同 crate 中互不重叠的实现。
- 一个调查者查根因，同时另一个只收集独立运行证据。
- 实现完成后，评审与文档核对读取同一稳定 diff。

必须串行：

- 同一文件、同一 schema、同一路由表或同一公开 API。
- `Cargo.toml` / `Cargo.lock` / 根 Agent 规范。
- 会同时触发根 `target/` 写锁的构建与测试。
- 前一步输出是后一步完整输入的 handoff 链。

Buzz 房间仍遵守“一条消息最多一个 `@Agent`”；编码 Agent 的并行也不得制造重叠写入或第二套实现。

## 5. 标准执行链

1. 接单：明确可观察验收点与不在范围内的事项。
2. 搜索：定位已有权威实现、调用方、测试和适用规范。
3. 所有权：为每个模块指定唯一写入者；先固定共享契约。
4. 实施：最小 diff，Rust-only，无脚本/TS 业务旁路。
5. 验证：最窄测试 → package check/test → 必要的跨 crate 或 UI smoke。
6. 评审：独立检查正确性、性能、并发、架构和测试缺口。
7. 交接：提供结果、证据、风险和下一责任人；完成后写回既有记忆机制。

## 6. 交接格式

```text
任务：一句话目标
状态：完成 / 阻塞 / 需要复核
所有权：本次负责的 crate、模块或文件
变更：已完成的可观察行为
验证：实际命令与结果
证据：关键路径、日志或测试名
风险：未覆盖平台、数据或边界
下一责任人：角色 + 只需继续的具体动作
```

阻塞交接必须说明已经排除什么、还缺什么；禁止只写“失败了”或让下一角色从零重查。

## 7. 完成判定

- 验收点可复现，验证结果不是口头推断。
- 只有一个权威实现点，没有同位复制。
- 代码在正确 crate，未新增脚本/多语言业务层或第二个 target。
- 评审发现已处理，或明确记录为用户可决定的残余风险。
- 交接信息足以让下一角色不重复探索。
